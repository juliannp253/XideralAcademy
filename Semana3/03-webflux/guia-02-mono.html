Antes de empezar

00 Poner en marcha

  • [ ]Java 21 o superior java -version debe decir 21 o más.
  • [ ]Haber leído la guía de conceptos — Pensar en flujos. Aquí se da por sabido qué es push, qué son los tres canales y qué es un Mono.
  • [ ]Nada más No hay Docker, ni MySQL, ni Mongo, ni contraseñas. A propósito: lo difícil de este tema es el concepto, no la instalación.

Si solo quieres verlo funcionar antes de escribir nada:

$ cd proyectos/01-webflux-mono
$ ./mvnw spring-boot:run
Netty started on port 8074 (http)
Started WebfluxMonoApplication in 1.08 seconds

# en otra terminal
$ ./scripts/probar.sh

Fíjate ya en una cosa. Dice Netty started, no Tomcat started. WebFlux no usa Tomcat: usa Netty, un servidor construido sobre un event loop de pocos hilos. Ese cambio de servidor es la mitad de la historia.

Los datos

02 Los datos y la latencia

El Employee es un record: inmutable, sin setters. Encaja con el estilo funcional del que hablaba la guía de conceptos — si nadie puede modificarlo, no hace falta sincronizar nada aunque lo toquen varios hilos.

model/Employee.java 
public record Employee(int id, String firstName, String lastName, String email) { }

El repositorio no habla con ninguna base de datos: los datos están en un Map. Pero simula lo único que nos importa de una base de datos real: que tarda.

repo/EmployeeRepository.java — el corazón del proyecto 
public static final Duration LATENCIA = Duration.ofMillis(5000);

// ── versión reactiva ──────────────────────────────────────
public Mono<Employee> findById(int id) {
    return Mono.justOrEmpty(tabla.get(id))   // si no está → Mono vacío
               .delayElement(LATENCIA);      // "la base de datos tarda"
}

// ── versión bloqueante (para el experimento de la §08) ────
public Employee findByIdBloqueante(int id) {
    Thread.sleep(LATENCIA.toMillis());     // el hilo se DUERME
    return tabla.get(id);
}

Las dos tardan 5 segundos. Esa es la clave del experimento final. No vamos a comparar una lenta con una rápida: vamos a comparar dos que tardan exactamente lo mismo. Lo único que cambia es si el hilo se queda esperando o se va a atender a otro. Guarda esa frase para la §08.

Y fíjate en lo que no pasa al llamar a findById(): no se busca nada, no se espera nada. Devuelve un Mono y el método termina de inmediato. Es la receta.

El código

03 El controlador

Aquí está la traducción completa desde el proyecto 15. Míralas juntas:

antes y después 
// ── Proyecto 15 · Spring MVC ──────────────────────────────
@GetMapping("/employees/{id}")
public Employee findById(@PathVariable int id) {
    return service.findById(id);        // el hilo espera AQUÍ 5 segundos
}

// ── Proyecto 01 · WebFlux ─────────────────────────────────
@GetMapping("/employees/{id}")
public Mono<Employee> findById(@PathVariable int id) {
    return repo.findById(id)             // devuelve el plan y suelta el hilo
               .switchIfEmpty(Mono.error(new ResponseStatusException(
                       HttpStatus.NOT_FOUND, "No existe el empleado " + id)));
}

Una palabra de diferencia en la firma. El cuerpo es el mismo. Lo que cambia es quién espera: en MVC espera tu hilo; en WebFlux no espera nadie, porque Spring se suscribe y suelta el hilo hasta que el dato esté.

Arráncalo y pruébalo:

$ curl -s -w '\n%{time_total}s\n' http://localhost:8074/api/employees/1
{"id":1,"firstName":"Leslie","lastName":"Andrews","email":"leslie@luv2code.com"}
5.017419s
Qué deberías ver

El JSON de siempre, y unos 5 segundos — la latencia que simulamos. Idéntico a lo que devolvía el proyecto 15. Y eso es exactamente el problema pedagógico de esta guía: con una sola petición, WebFlux y MVC son indistinguibles. La diferencia no aparece hasta la §08.

La primera sorpresa

04 El vacío no es un error

Casi todo el mundo da por hecho que si el Mono viene vacío, Spring devuelve un 404. Vamos a comprobarlo. Añade este endpoint, que es igual que el anterior pero sin switchIfEmpty:

@GetMapping("/employees-suave/{id}")
public Mono<Employee> findByIdSuave(@PathVariable int id) {
    return repo.findById(id);        // sin switchIfEmpty
}
$ curl -i http://localhost:8074/api/employees-suave/999
HTTP/1.1 200 OK
content-length: 0

# …y ahora el que SÍ lleva switchIfEmpty:
$ curl -i http://localhost:8074/api/employees/999
HTTP/1.1 404 Not Found
{"timestamp":"…","path":"/api/employees/999","status":404,
 "error":"Not Found","requestId":"…","message":"No existe el empleado 999"}

200 OK con el cuerpo vacío. No 404. Y no es un fallo de Spring: es coherente con lo que aprendiste en la guía de conceptos. Un Mono vacío es un flujo que hizo onComplete sin ningún onNext, y eso es un final feliz. En el modelo reactivo, “no hay nada” no es un error — es una respuesta legítima.

Si quieres un 404, tienes que pedirlo. Eso es lo que hace switchIfEmpty(): “si el flujo termina sin emitir, cámbialo por este otro” — y ese otro es un Mono.error(...).

El tercer canal

05 El canal de error

Ahora vas a manejar un error sin un solo try/catch. Este endpoint truena a propósito y se recupera solo:

@GetMapping("/employees/{id}/boom")
public Mono<Employee> boom(@PathVariable int id) {
    return repo.findById(id)
               .flatMap(e -> Mono.<Employee>error(new IllegalStateException("truena")))
               .onErrorResume(ex -> {                 // ← aquí está tu catch
                   log.warn("me lo comí: {}", ex.getMessage());
                   return Mono.just(new Employee(-1, "Plan", "B", "fallback@academymty.mx"));
               });
}
Qué deberías ver

{"id":-1,"firstName":"Plan","lastName":"B",…} con un 200. El error ocurrió de verdad — lo ves en el log del servidor— pero onErrorResume lo sustituyó por un valor de repuesto dentro del flujo, y el cliente ni se enteró.

Esto es lo que la guía de conceptos llamaba “el error es un ciudadano de primera clase”. Como viaja por el flujo y no por la pila de llamadas, puedes aplicarle operadores: sustituirlo (onErrorResume), reintentarlo con espera creciente (retryWhen), o cambiar de fuente. Con try/catch solo puedes atraparlo y decidir ahí mismo.

Y un tipo que no existe en el mundo bloqueante:

@DeleteMapping("/employees/{id}")
public Mono<Void> delete(@PathVariable int id) {
    return repo.findById(id).then();   // then() tira el valor, deja la señal de fin
}

Mono<Void> es “no te devuelvo nada, pero te aviso cuando haya terminado”. Es el void reactivo — y a diferencia de un void normal, sí puedes esperarlo.

La prueba

06 ¿Quién te atiende?

Hasta aquí todo ha sido igual que MVC. Esta es la primera evidencia real de que algo cambió por debajo:

$ for i in 1 2 3 4 5; do curl -s localhost:8074/api/hilo | cut -d, -f1; done
{"hilo":"reactor-http-nio-8"
{"hilo":"reactor-http-nio-9"
{"hilo":"reactor-http-nio-1"
{"hilo":"reactor-http-nio-10"
{"hilo":"reactor-http-nio-2"
Qué deberías ver

Nombres reactor-http-nio-N que se repiten. Si haces 100 peticiones no verás 100 hilos: verás los mismos pocos, tantos como núcleos tenga tu máquina. Eso es el event loop.

En el proyecto 15, con Tomcat, verías http-nio-8080-exec-1, -exec-2, -exec-3… uno distinto por petición, hasta 200.

Y de aquí sale la regla de oro. Si solo tienes 8 hilos para atender todo el tráfico, ninguno puede pararse jamás. Un Thread.sleep(), una consulta JDBC o un RestTemplate escondidos en un map() no ralentizan una petición: congelan el servidor entero. Es exactamente lo que vas a medir en la §08.

El momento clave

07 Donde se entiende de verdad

En el controlador nunca notas que un Mono es una receta, porque Spring se suscribe por ti. En un test no hay nadie que lo haga — y ahí cae la ficha:

src/test/java/…/EmployeeRepositoryTest.java 
@Test
void sinSubscribeNoPasaNada() {
    AtomicBoolean seEjecuto = new AtomicBoolean(false);

    Mono<String> receta = Mono.fromCallable(() -> {
        seEjecuto.set(true);
        return "cocinado";
    });

    // Ya construimos el Mono. ¿Se ejecutó el código de dentro?
    assertFalse(seEjecuto.get());     // ← NO. Es la receta, no el plato.

    receta.block();                   // block() se suscribe y espera

    assertTrue(seEjecuto.get());      // ← ahora sí
}

Este test es la guía entera en veinte líneas. Construir el Mono no ejecuta nada. Ni una consulta, ni una petición HTTP, ni un println. Todo espera a que alguien se suscriba. Cuando alguien te diga “mi código reactivo no hace nada y no marca error”, es esto el 90 % de las veces.

StepVerifier: cómo se testea de verdad

.block() vale para demostrar el punto, pero no es la forma correcta. La herramienta es StepVerifier, y lee casi como una frase — porque comprueba las señales que estudiaste en la guía de conceptos:

@Test
void empleadoQueExiste() {
    StepVerifier.create(repo.findById(1))
            .assertNext(e -> assertEquals("Leslie", e.firstName()))   // onNext
            .verifyComplete();                                        // onComplete
}

@Test
void empleadoQueNoExiste() {
    StepVerifier.create(repo.findById(999))
            .verifyComplete();      // cero onNext, directo a onComplete ← la §04
}

@Test
void elErrorEsUnaSenal() {
    StepVerifier.create(repo.findById(1).flatMap(e -> Mono.error(new IllegalStateException())))
            .verifyError(IllegalStateException.class);   // onError, no una excepción lanzada
}
$ ./mvnw test
Tests run: 6, Failures: 0, Errors: 0, Skipped: 0
BUILD SUCCESS

Un test que protege la lección

Hay un sexto test, y existe por un motivo que descubrimos rompiendo el código a propósito: si alguien borra el .delayElement(LATENCIA) del repositorio, el experimento de la §08 deja de mostrar diferencia y el proyecto pierde el sentido… pero los otros cinco tests siguen en verde. Este lo caza:

@Test
void tardaLoQueDebeTardar() {
    StepVerifier.withVirtualTime(() -> repo.findById(1))
            .expectSubscription()
            .expectNoEvent(EmployeeRepository.LATENCIA)   // 5 segundos de SILENCIO
            .assertNext(e -> assertEquals("Leslie", e.firstName()))
            .verifyComplete();
}

expectNoEvent(d) comprueba que durante ese tiempo no llega ninguna señal. Es la forma de testear que algo tarda, sin esperar de verdad.

Y un detalle que evita perder una tarde. Un StepVerifier que espera una señal que nunca llega se queda colgado para siempre, no falla. En este proyecto lo comprobamos rompiendo la cadencia a propósito: la suite se colgó ocho minutos hasta que la matamos. Con una línea deja de pasar — y los mismos tests fallan en 15 segundos en vez de colgarse:

@BeforeAll
static void noColgarseNunca() {
    StepVerifier.setDefaultTimeout(EmployeeRepository.LATENCIA.plusSeconds(10));
}

.block() solo en tests y en main(). Dentro de un @RestController de WebFlux bloquea un hilo del event loop — y ya sabes lo que eso significa. Reactor lo detecta y lanza IllegalStateException: block()/blockFirst()/blockLast() are blocking, which is not supported in thread reactor-http-nio-2. Cuando veas ese mensaje, no lo silencies: te está salvando.

El experimento

08 Ahora sí: la diferencia

Todo lo anterior se veía igual que el proyecto 15. Vamos a hacer que deje de verse igual.

En la misma aplicación hay un segundo controlador. Es el código del proyecto 15, copiado tal cual, dentro de una app WebFlux:

rest/BloqueanteRestController.java — LO QUE NO HAY QUE HACER 
@RestController
@RequestMapping("/api/mvc")
public class BloqueanteRestController {

    @GetMapping("/employees/{id}")
    public Employee findByIdBloqueante(@PathVariable int id) {
        return repo.findByIdBloqueante(id);   // Thread.sleep() sobre el event loop
    }
}

Compila. Arranca. Devuelve el mismo JSON. Y tarda los mismos 5 segundos si haces una petición. Ahora hazle 100 a la vez:

$ ./scripts/comparar.sh 100

  Tu maquina tiene 10 nucleos, asi que el event loop de Netty tiene
  ~10 hilos. Lanzamos 100 peticiones CONCURRENTES a cada ruta.

  Prediccion antes de correrlo:
    reactivo    -> ~5.0s   (ningun hilo espera: las 100 se solapan)
    bloqueante  -> ~50.00s   (100 peticiones / 10 hilos = 10.0 tandas de 5.0s)

  reactivo     100 peticiones en   5.13 s
  bloqueante   100 peticiones en  50.13 s
Qué deberías ver

El reactivo tarda lo mismo que una sola petición — porque las 100 se solapan. El bloqueante tarda unas 10 veces más, y el número no es magia: es 100 peticiones ÷ 10 hilos × 5 s. Si tu máquina tiene 4 núcleos te saldrá peor; si tiene 16, mejor. Predice tu número antes de correrlo y comprueba que cuadra.

Qué demuestra exactamente (y qué no)

  • No demuestra que “reactivo sea rápido”. Las dos rutas tardan 5 segundos en el dato, y una sola petición tarda igual en las dos. Reactivo no acelera nada.
  • Demuestra que el bloqueante desperdicia. Duerme sus 10 hilos y por eso las peticiones hacen cola. El reactivo los suelta y no encola. La métrica que mejora es el throughput, no la latencia — justo lo que el anexo de erratas señala como impreciso en el mapa mental.
  • Y demuestra la trampa del §07 de la guía de conceptos. Ese controlador bloqueante no es un ejemplo rebuscado: es lo que pasa si migras a WebFlux y dejas el repositorio con JPA/JDBC. Habrás cambiado los 200 hilos de Tomcat por 10 de Netty, y los bloqueas igual. Quedas peor que antes de migrar.

La conclusión que se llevan a casa. WebFlux no es un interruptor que se enciende cambiando el tipo de retorno. O toda la pila es no bloqueante — repositorio incluido— o no sirve de nada. Por eso existen R2DBC y los drivers reactivos de MongoDB: sin ellos, un Mono es solo un Employee con más letras.

Si algo falla

01 “Web server failed to start. Port 8074 was already in use”Tienes otra app viva. lsof -i :8074 para ver quién, o cambia server.port.
02 Arranca con Tomcat started en vez de Netty startedTe colaste de starter: tienes spring-boot-starter-webmvc en el pom.xml. Si están los dos, gana MVC y WebFlux queda desactivado.
03 cannot find symbol: com.fasterxml.jackson…Boot 4 trae Jackson 3, cuyo paquete es tools.jackson.core. Ese import solo aparece si copiaste configuración de un tutorial de Boot 3.
04 El endpoint devuelve 200 con cuerpo vacío en vez de 404No es un bug: es la §04. Un Mono vacío es un final feliz. Añade switchIfEmpty().
05 IllegalStateException: block()… not supported in thread reactor-http-nio-NLlamaste a .block() dentro de un controlador. Devuelve el Mono y deja que Spring se suscriba.
06 El test pasa pero no comprueba nada¿Te suscribiste? Un Mono construido y nunca suscrito no ejecuta su contenido, así que un assert sobre sus efectos siempre falla en silencio. Usa StepVerifier.

Si trabajas en Windows. Usa mvnw.cmd spring-boot:run en lugar de ./mvnw. Los .sh de scripts/ necesitan Git Bash o WSL; en PowerShell, curl es un alias de Invoke-WebRequest y se comporta distinto — usa curl.exe explícitamente.

Ejercicios

  • 1Predice antes de medir Mira cuántos núcleos tiene tu máquina y calcula qué va a tardar ./scripts/comparar.sh 200 en la ruta bloqueante. Después córrelo. ¿Cuadró?
  • 2Rompe el reactivo Mete un Thread.sleep(5000) dentro del map() del controlador reactivo — sin tocar el tipo de retorno, que sigue siendo Mono. Vuelve a medir. ¿Sigue siendo reactivo? Esta es la trampa más cara del tema.
  • 3Arréglalo Ahora aísla ese bloqueo con .subscribeOn(Schedulers.boundedElastic()) y mide otra vez. ¿Qué cambió y por qué?
  • 4404 sin excepción Consigue que /api/employees-suave/999 devuelva 404 sin lanzar ninguna excepción. Pista: defaultIfEmpty no sirve; mira ResponseEntity.
  • 5Reintentos Haz que el endpoint /boom reintente tres veces con espera creciente antes de rendirse, usando retryWhen(Retry.backoff(3, Duration.ofMillis(200))). Añade un doOnError para ver los intentos en el log.
  • 6El puente Escribe un test que demuestre que Mono.just(cargar()) ejecuta cargar() de inmediato, mientras que Mono.defer(() -> Mono.just(cargar())) espera a la suscripción. Es la trampa 06 de la guía de conceptos.
