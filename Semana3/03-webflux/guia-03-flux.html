La pregunta que responde este laboratorio. Si un Flux<Lectura> acaba llegando al navegador como un array JSON, exactamente igual que el List<Employee> del proyecto 15… ¿para qué sirve? Es una pregunta legítima, y casi ningún tutorial la contesta. Vamos a contestarla enseñándotela.

La fuente

01 Un sensor en cuatro líneas

El dominio no es casual. El mapa mental lista “agregar información de sensores de temperatura para controlar la calefacción” como caso de uso reactivo. Un empleado que llega cada segundo sería artificial; un sensor no lo es.

service/SensorService.java — todo el proyecto está aquí 
public Flux<Lectura> lecturas() {
    return Flux.interval(Duration.ofSeconds(1))   // 0, 1, 2, 3… para siempre
               .map(this::medir);
}

private Lectura medir(long n) {
    double celsius = 26 + 8 * Math.sin(2 * Math.PI * n / 20.0);
    return new Lectura(n, "sensor-A", redondear(celsius), ahora());
}

Flux.interval(1s) emite 0, 1, 2, 3… uno por segundo, y no para nunca. Es un flujo infinito: jamás manda onComplete.

Eso es lo que una List<T> no puede representar. No es que sea incómodo: es imposible. Una lista tiene un tamaño; para dártela hay que terminarla primero. Un flujo que no termina nunca no cabe en una lista, y esa es la razón de que Flux exista.

La temperatura sigue una onda entre ~18 y ~34 °C con ciclos de 20 segundos. Es a propósito y no aleatorio: así las alertas de la §04 se disparan de forma predecible y puedes comprobar que el filtro hace lo que dice.

El corazón de la guía

02 La misma fuente, dos formas

Dos endpoints. Mismo servicio, mismo tipo de retorno, mismos datos. Lo único que cambia es el produces:

rest/LecturaRestController.java 
// (A) JSON normal
@GetMapping(produces = MediaType.APPLICATION_JSON_VALUE)
public Flux<Lectura> comoJson() {
    return sensor.lecturas().take(5);
}

// (B) El MISMO Flux, como stream de eventos
@GetMapping(path = "/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public Flux<Lectura> comoStream() {
    return sensor.lecturas().take(20);
}

La -N de curl es obligatoria. Desactiva el buffer de salida. Sin ella, curl acumula por su cuenta y verías lo mismo que en (A) — y concluirías, equivocadamente, que el streaming no funciona. Es el error más común de esta sección.

Qué está pasando por debajo

A application/jsonSpring se suscribe, acumula todas las lecturas, espera al onComplete, y solo entonces serializa el array y lo manda. Por dentro está haciendo un collectList() — que, como verás en la §06, convierte un Flux en un Mono. De ahí que se comporte como una lista.
B text/event-streamSpring no acumula nada. Cada onNext se serializa y sale por el cable en cuanto existe, con la conexión HTTP abierta. Es Server-Sent Events, un estándar del navegador desde hace más de una década.

Esta es la respuesta a la pregunta de la §00. Un Flux no sirve “para devolver listas con otro nombre”. Sirve para lo que un List no puede: entregar datos conforme existen, sin esperar a que estén todos, sobre una secuencia que quizá no termine nunca.

El momento del clic

03 Verlo en el navegador

La terminal ya lo enseña, pero lado a lado es imbatible. El proyecto trae una página en src/main/resources/static/index.html. Abre http://localhost:8075 y dale a los dos botones a la vez:

El panel B usa EventSource, la API que el navegador trae de fábrica para consumir text/event-stream. Son cinco líneas de JavaScript, sin librerías:

const es = new EventSource('/api/lecturas/stream');

es.onmessage = function (ev) {
    const lectura = JSON.parse(ev.data);   // ← se ejecuta UNA VEZ POR LECTURA
    pintar(lectura);
};

es.onerror = function () {
    // el servidor mandó onComplete (tras take(20)) y cerró
    es.close();
};
Qué deberías ver

El panel izquierdo vacío durante cinco segundos mientras el derecho ya va por la cuarta o quinta lectura. Cuando el izquierdo por fin se llena, el derecho le saca cinco de ventaja y sigue.

Deja el derecho abierto: a las 20 lecturas el servidor manda onComplete y la conexión se cierra sola. Eso es el flujo terminando de forma limpia.

Y aquí es donde encaja todo lo de la guía de conceptos. Cada línea que aparece en el panel B es un onNext. El cierre limpio del final es un onComplete. Si el sensor fallara, sería un onError — y el onerror del EventSource es literalmente ese tercer canal, cruzando la red hasta el navegador.

El valor real

04 Operadores sobre un flujo vivo

Con los datos ya llegando, los operadores dejan de parecer azúcar sintáctico. filter() sobre un flujo infinito:

@GetMapping(path = "/alertas", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public Flux<Lectura> alertas(@RequestParam(defaultValue = "30") double umbral) {
    return sensor.lecturas()
                 .filter(l -> l.celsius() > umbral)
                 .doOnNext(l -> log.warn("ALERTA {} C", l.celsius()));
}
$ curl -N -s "localhost:8075/api/lecturas/alertas?umbral=30"
data:{"numero":2,"sensor":"sensor-A","celsius":30.7,"hora":"14:35:09"}
data:{"numero":3,"sensor":"sensor-A","celsius":32.5,"hora":"14:35:10"}
data:{"numero":4,"sensor":"sensor-A","celsius":33.6,"hora":"14:35:11"}
          ⋮  y luego SILENCIO mientras la onda baja
Qué deberías ver

Rachas de alertas seguidas de silencios largos, siguiendo la onda de 20 segundos. Y algo que conviene entender bien: durante el silencio el flujo no se ha parado. Sigue emitiendo una lectura por segundo — el filter simplemente no las deja pasar. Míralo en el log del servidor: ahí sí siguen apareciendo.

Escribir esto a mano con hilos —un bucle, una condición, y mandar el resultado por un socket abierto sin bloquear a nadie— es perfectamente posible y es exactamente el tipo de código que nadie quiere mantener. Eso es lo que el mapa mental llamaba composición declarativa.

El ejemplo del mapa

05 Un flujo que se cierra solo

El mapa mental trae este caso literal: “vigila el precio de la acción hasta que baje de 100”. Cámbiale el dominio y es takeUntil():

@GetMapping(path = "/hasta/{umbral}", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public Flux<Lectura> hasta(@PathVariable double umbral) {
    return sensor.lecturas()
                 .takeUntil(l -> l.celsius() < umbral)
                 .doOnComplete(() -> log.info("bajó de {} C: onComplete y cierro", umbral));
}
$ curl -N -s localhost:8075/api/lecturas/hasta/20
data:{"numero":12,"sensor":"sensor-A","celsius":21.3,…}
data:{"numero":13,"sensor":"sensor-A","celsius":19.5,…}
$ # ← el prompt vuelve SOLO, sin Ctrl-C
Qué deberías ver

Lecturas durante unos 14 segundos y después el prompt de vuelta sin que aprietes nada. Un flujo infinito se volvió finito porque se cumplió una condición: takeUntil emitió el elemento que la cumple, mandó onComplete, y Spring cerró la conexión HTTP.

Fíjate en lo que acabas de montar. Un cliente conectado a un servidor que le manda datos en tiempo real y le cierra la conexión limpiamente cuando se cumple una condición de negocio — en tres líneas, sin gestionar un solo hilo, un solo socket ni un solo temporizador. Ese es el argumento de WebFlux que los virtual threads no reemplazan, y por eso la §10 de la guía de conceptos lo deja en la columna de “lo que no cambió”.

El puente

06 De vuelta a Mono

Un Flux puede colapsarse en un solo valor, y ahí vuelve a ser un Mono:

@GetMapping(path = "/resumen", produces = MediaType.APPLICATION_JSON_VALUE)
public Mono<Map<String, Object>> resumen() {
    return sensor.lecturas()
                 .take(10)
                 .collectList()      // Flux<Lectura> → Mono<List<Lectura>>
                 .map(this::estadisticas);
}
$ curl -s localhost:8075/api/lecturas/resumen   # tarda 10 s
{"lecturas":10,"minima":26.0,"maxima":34.0,"promedio":31.1,
 "masCaliente":{"numero":5,"sensor":"sensor-A","celsius":34.0,"hora":"14:35:31"}}

collectList() espera a que el flujo termine y devuelve todo junto: por eso el tipo pasa a ser Mono<…>, un solo valor.

Y esto cierra el círculo de la §02. ¿Por qué el endpoint (A) se comportaba como una lista? Porque servir un Flux como application/json hace exactamente esto por debajo. No es que el Flux “se convierta en lista”: es que el formato JSON te obliga a tener el array completo antes de escribir el primer corchete. El límite no está en Reactor, está en el Content-Type.

La herramienta

07 Testear el tiempo sin esperarlo

Un flujo de una lectura por segundo tiene un problema obvio en un test: comprobar 20 lecturas tardaría 20 segundos. La solución es adelantar el reloj:

@Test
void emiteEnOrden() {
    StepVerifier.withVirtualTime(() -> sensor.lecturas().take(3))
            .thenAwait(Duration.ofSeconds(3))     // 3 segundos… de mentira
            .assertNext(l -> assertEquals(0, l.numero()))
            .assertNext(l -> assertEquals(1, l.numero()))
            .assertNext(l -> assertEquals(2, l.numero()))
            .verifyComplete();
}

@Test
void esInfinito() {
    StepVerifier.withVirtualTime(sensor::lecturas)
            .thenAwait(Duration.ofSeconds(30))
            .expectNextCount(30)
            .thenCancel()        // hay que cancelarlo: solo no para nunca
            .verify();
}

Ponle siempre un límite al verificador. Si un StepVerifier espera una señal que nunca llega, se cuelga para siempre en vez de fallar — y revienta el build. Lo comprobamos rompiendo la cadencia del sensor a propósito: la suite se quedó colgada ocho minutos. Con StepVerifier.setDefaultTimeout(Duration.ofSeconds(10)) en un @BeforeAll, esa misma rotura da 5 fallos limpios en 50 segundos.

La trampa de withVirtualTime, y es sutil. El Flux tiene que construirse dentro del lambda. Si lo montas antes:

// MAL — 20 segundos reales
Flux<Lectura> calientes = sensor.lecturas().take(20).filter(...);
StepVerifier.withVirtualTime(() -> calientes)

// BIEN — 0,2 segundos
StepVerifier.withVirtualTime(() -> sensor.lecturas().take(20).filter(...))

…entonces Flux.interval() ya se quedó con el planificador de verdad en el momento de montarse, porque withVirtualTime instala el reloj falso justo antes de ejecutar el lambda. En este proyecto la diferencia medida fue de 20,23 s a 0,19 s en ese único test. El test pasa en los dos casos — solo que uno tarda cien veces más y no te dice por qué.

$ ./mvnw test
Tests run: 5, Failures: 0, Errors: 0, Skipped: 0 -- Time elapsed: 0.116 s
BUILD SUCCESS

Cinco tests que cubren 78 segundos de flujo, en una décima de segundo.

Referencia

Si algo falla

01 El stream llega de golpe, no goteandoTe faltó la -N de curl. Sin ella curl acumula por su cuenta y no ves nada hasta el final. En el navegador esto no pasa.
02 /api/lecturas no responde nunca¿Le quitaste el .take(5)? Sin él, servir un flujo infinito como JSON es esperar a que termine algo que no termina. El navegador se queda colgado para siempre — y es el comportamiento correcto.
03 El EventSource reconecta solo cada pocos segundosNo es un bug tuyo: es el estándar. Cuando la conexión se cierra, el navegador reintenta. Por eso el ejemplo llama a es.close() dentro de onerror.
04 Los tests tardan 20 segundosEs la trampa de la §07: construiste el Flux fuera del lambda de withVirtualTime.
05 Las alertas no salen nuncaSube el umbral por encima de 34 y no saldrá ninguna: la onda no llega. Prueba con ?umbral=30 y espera al menos 20 segundos, que es un ciclo completo.
